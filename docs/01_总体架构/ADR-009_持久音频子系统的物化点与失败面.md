# ADR-009：持久音频子系统的物化点与失败面

## 1. 背景与证据边界

PRD §20.2 要求 Story Book 的聆听模式「重用 Story Session 已生成音频」。核验时间
2026-10-03，运行环境 macOS 26+ / arm64。以下均为源码穷尽核实，非文档转述。

`docs/PROJECT_STATE.json` 的 `verified_unwired.PERSISTENT-AUDIO-SUBSYSTEM` 已记录
「take 层本身零生产调用方」。本 ADR 在此之上补齐三件此前未记录的事实，并据此把
待裁问题从「发布时机与 redub 策略」改写为可裁的四个子问题。

### 1.1 当前音频形态：封存的是配方，不是音频

一次已提交回合的音频经过的完整链路是：

```
COMMIT ──▶ post_commit_jobs(kind='audio_prepare')
        ──▶ ScenarioAudioPrepareHandler.execute()
              ├─ SpeechUnitSealingService.seal(...)  → SealedSpeechUnit（配方 + 证据 pin）
              ├─ _persist_sealed_result(...)          → post_commit_job_results（不可变结果记录）
              └─ VoiceRenderRuntime.publish(unit)     → 仅内存注册表

App 打开媒体流 ──▶ VoiceRenderRuntime.media_handler()
                     └─ render_realtime_tts_to_media(adapter, req, opened, reader, writer)
                          └─ PCM 逐 chunk 写 socket，无累积、不落库
```

`ScenarioAudioPrepareHandler` 的类文档字符串即「Seal and durably hand off only an
already-published narrative segment」；`execute()` 全程不调用 provider，`render_execution`
只构造执行身份而非发起渲染。`media_bridge.py` 的 `deliver_chunk` 直接
`await stream.push(chunk)`，不经任何缓冲。

**结论：全链路没有任何一点把音频字节物化为持久事实。** 已提交的是配方，播完即弃的是字节。

### 1.2 每个已提交回合最多一段拿到音频

三处叠加，把「逐段配音」压到只剩第一段：

| 位置 | 事实 |
|:---|:---|
| `application/post_commit_work.py` `required_jobs_for_turn` | 每回合只 `jobs.append` **一个** `AUDIO_PREPARE` |
| `infrastructure/scenarios/post_commit_planning.py` | `_recipe_revision` = `rules_revision + 常量`，同一 kind 恒定 |
| 迁移 013 `post_commit_jobs` | `UNIQUE(turn_id, kind, recipe_revision)`，第二行插不进去 |
| `scenarios/post_commit_handlers.py` | `candidates[0] if candidates else (None, None)`，只取**第一个** character 段 |

handler 的注释还说明 narration 段是**被故意**排除的：NarrativeBlock 尚无显式旁白身份，
放行等于让调用方选择谁来叙述整个游戏（这正是 ADR-006 D1 的边界，与
`ADR006-NARRATION-VOICE` 待裁决项同源）。

### 1.3 第三问已有承载形状：post-commit 失败面

`落库失败不得反向影响已 COMMIT 的叙事`（不变量 9）在 post-commit 层已有现成机制：

- `post_commit_jobs` 状态机 `pending / running / retry_wait / blocked / succeeded`，
  带 `attempt` / `last_error_code` / `lease_generation`；
- `post_commit_job_results` 存不可变结果记录，`post_commit_retry_requests` 承接幂等重试；
- `ScenarioAudioPrepareHandler.execute()` 的每条失败分支都返回 `_blocked(<code>)`，
  没有任何分支改写已提交事实；注释明写「Durable sealed state survives a failed in-memory handoff」；
- `post_commit_control.py` 模块文档字符串：「never rewrites a committed Domain turn」。

且这条链路**是接线的**：`story_runtime.py` 在生产路径上构造
`SQLitePostCommitJobRepository` 与 `ScenarioAudioPrepareHandler`，
`post_commit_worker.py` 按 kind 分发。

### 1.4 take 层与回放侧：机制齐备，零生产调用方

- `publish_pcm` 是写入 `audio_takes` 的唯一入口，全仓唯一的 `INSERT INTO audio_takes`
  也在 `engine/infrastructure/audio_take_store.py` 内；该方法只被
  `audio_take_coordinator` 调用，coordinator 只被 `audio_prefetch` 引用，
  而 prefetch 零生产调用方。
- 回放侧已建好：迁移 007 的 `audio_track_units` 逐段记录 `take_id` 并外键到
  `turn_transactions(id)` 与 `narrative_blocks(id)`；
  `OfflineStoryBookReplayResolver` 直接读钉住的 `take_id`，全程 storage-only。
- 这不是被实时流取代的死代码：[ADR-005](ADR-005_音色供给与铸造_v1.0.md) D7 把 take 当一等
  持久事实（「播放原缓存并保留原证据」「显式重播使用单独的新 take」），
  迁移 007 的 `kind='redub'` + `supersedes_track_id` + `UNIQUE(track_family_id, revision)`
  在 schema 层挡住了「重铸后回放播错音频」。
- `storybook.schema.json` 的 15 个字段全叙事、无音频；App 侧 `StoryBookModel` /
  `StoryBookView` 亦无音频呈现。

本节只确认「是什么」，不推断「应该是什么」。

## 2. 问题陈述

§1.1 把待裁问题从「接不接线」改写成了「音频字节是否应成为持久事实，若应在哪一点物化」。
四个子问题彼此依赖，1 是其余三个的前提：

1. **物化点**：音频字节是否应落库？若应，在链路的哪一点物化——
   (a) 封存配方时同点渲染并落 take；(b) 播放时旁路 tee；(c) 独立的预渲染 job；
   (d) 不落库，改由回放时按需重渲。
2. **覆盖范围**：若落库，是每回合一段（维持 §1.2 现状）还是逐段？
   PRD §20.2 与 ADR-005 验收标准 1「按身份逐段配音」在字面上要求后者。
3. **回放来源**：落库后的 take 是否即回放的唯一来源，还是允许回放时按需重渲？
   前者保真但占存储，后者省存储但可能播出与当时不同的音频。
4. **失败面**：落库失败如何表达？§1.3 的 `blocked` / `retry_wait` 是否已足够，
   还是要为「音频未落库」单列一个对 App 可见的状态？

## 3. 为什么不能由实现侧自行选定

1. **不变量 9 与 ADR-005 D7 的边界**：D7 已把 take 定为一等持久事实，但从未定义
   「谁在什么条件下有权让音频成为持久事实」。选 (d) 等于事实上推翻 D7 的一部分；
   选 (a)/(b)/(c) 则要定义新的物化点及其失败语义。这是架构决定，不是实现选择。
2. **不变量 11（权威持久与可重建分离）**：`audio_takes` 在 `world.db`（权威），
   而回放是读模型。若选 (d)，则权威库里将永远没有音频，Story Book 的聆听模式
   只能靠重渲，而重渲结果无法回溯到「当时播过什么」——这与不变量 9 的
   「提交即命运」是同一枚硬币的两面。
3. **§1.2 的天花板不是疏漏，是当前设计**：把每回合一段改成逐段，
   意味着 job 规划、recipe 身份与 `UNIQUE` 约束都要改；改法有多种，
   哪一种符合「一回合一次表达」的语义，需要人类定。
4. **ADR-006 待裁决**：narration 段是否进入配音路径未定。若裁定进入，
   §1.2 的候选集从「第一个 character 段」变为「所有段」，2 的成本随之变化。
   两项裁决必须一起看，但**不得由实现侧代为合并**。

## 4. 候选方案

以下方案均满足第 3 节的约束，差别在物化点、保真度与成本。

### 4.1 子问题 1：物化点

| | 读出的内容 | 新增迁移 | 实现成本 | 主要代价 |
|:---|:---|:---|:---|:---|
| **1-a 同点渲染** 封存配方时即渲染并落 take | 与提交时完全一致的音频 | 无（表已存在） | 中 | 把 provider 调用搬进 post-commit job，失败面变宽；`audio_prepare` 由「不调 provider」变为「调 provider」，与 §1.3 的 sealed-only 语义冲突 |
| **1-b 播放时 tee** 播放路径顺带落库 | 实际播出的音频 | 无 | 中高 | 实时流是 chunk 推送，`publish_pcm` 要求完整 PCM（既有守卫 `test_a_take_cannot_be_teed_off_the_realtime_stream` 已钉死这不是一行 tee）；且落库发生在播放侧，失败与播放耦合 |
| **1-c 独立预渲染 job** 提交后异步渲染整段并落 take | 与提交时一致的音频，且不拖慢播放 | 无 | 高 | 需扩展 job 规划以覆盖多段（见 2）；provider 成本翻倍 |
| **1-d 不落库** 回放时按需重渲 | 「重渲后的当前最佳音色」 | 无 | 低 | 与 ADR-005 D7 冲突；无法回溯「当时播过什么」；Story Book 聆听模式与 Story Session 的音频不再同一份 |

### 4.2 子问题 2：覆盖范围

维持每回合一段（零成本、与 §1.2 现状一致），或改为逐段（符合 §20.2 字面要求，
但需改 job 规划与 `UNIQUE(turn_id, kind, recipe_revision)` 约束——按段引入 recipe 身份维度）。
**注意**：本项在 1-d 下无意义（没有 take 可钉），因此 1 先于 2。

### 4.3 子问题 3：回放来源

take 为唯一来源（保真、可回溯，与 D7 一致），或允许按需重渲（省存储、但可能播出
与提交时不同的音频）。迁移 007 的 `kind='redub'` + `supersedes_track_id` 已使
「显式重播使用单独的新 take」在 schema 层可行，因此两者都不是结构性障碍，
差别在产品是否接受「同一段两次播出不同音频」。

### 4.4 子问题 4：失败面

沿用 `blocked` / `retry_wait`（零新增契约，App 已能读到 `audio_prepare` 的公开状态），
或为「音频未落库」单列状态（需扩 `story_post_commit_control` 契约与 App 呈现）。

### 4.5 对照

| | 保真 D7 | 触及不变量 9 | 新增迁移 | 新增契约 | 实现成本 |
|:---|:---|:---|:---|:---|:---|
| 1-a 同点渲染 | 是 | 是（失败面变宽） | 无 | 无 | 中 |
| 1-b 播放时 tee | 是 | 是（与播放耦合） | 无 | 无 | 中高 |
| 1-c 独立预渲染 job | 是 | 否（已有 job 面承载） | 无 | job 规划扩展 | 高 |
| 1-d 不落库 | **否** | 否 | 无 | 无 | 低 |

## 5. 迁移、兼容与回退

四个物化点方案都**不需要新增迁移**：`audio_takes` 与 `audio_track_units` 已存在，
缺的只是生产调用方。因此回退代价低——撤掉接线即可，既有数据不需迁移。

子问题 2 若选逐段，则 `post_commit_jobs` 需要按段引入 recipe 身份维度，
属迁移 013 的前向变更，须按 ADR-002 的前向迁移纪律单独立项。

子问题 4 若选新增状态，则 `story_post_commit_control.schema.json` 的公共接口变更
须同步 Swift 侧，且属 `.hacf/` 受保护面之外的 `contracts/` 高风险面，需仲裁扩权。

## 6. 测试策略

选定后至少需要：

- 物化点：一条测试断言 take 的字节与当次渲染所用配方一致（1-a / 1-b / 1-c 各自的口径不同）；
- 覆盖范围：一条测试断言每个应发音段都有 take（逐段方案）或明确断言只有第一段（维持现状）；
- 回放来源：一条测试断言重铸后回放播的是钉住的旧 take，而非重渲；
- 失败面：一条测试断言落库失败时已提交叙事未被改写（不变量 9），且失败状态对 App 可见；
- 既有守卫继续有效：`check_storybook_reading_path_is_model_free`（SB-18）覆盖阅读路径零 model；
  `test_a_take_cannot_be_teed_off_the_realtime_stream` 覆盖「不是一行 tee」；
  `test_the_take_layer_itself_has_no_production_caller` 覆盖 take 层零调用方——
  **接线完成后这三条守卫会转红，届时必须逐条更新而非删除**，它们记录的是接线前的事实。

## 7. 与既有决策的关系

- **ADR-005 D7**：把 take 定为一等持久事实。本 ADR 的 1-d 与之冲突，须由人类明示是否推翻。
- **不变量 9**（提交即命运）：1-a / 1-b 扩大了 provider 失败面，1-c 最小，1-d 无失败面。
- **不变量 11**：`audio_takes` 在权威库、回放为读模型；1-d 下权威库永无音频。
- **ADR-006 D1**：旁白身份未定，直接决定子问题 2 的候选集大小（见 §3.4）。
- **ADR-008**：同属 Story Book 收口，但裁的是叙事第五段；本 ADR 裁的是音频面。两者可独立裁决。

## 8. 决策状态

**待裁决**。需人类架构师裁定：

1. **物化点**：在 4.1 的 1-a / 1-b / 1-c / 1-d 中选其一（先决，其余依赖它）；
2. **覆盖范围**：维持每回合一段，还是改为逐段（§4.2）；
3. **回放来源**：take 是否唯一来源（§4.3）；
4. **失败面**：沿用 `blocked` / `retry_wait`，还是新增状态（§4.4）。

其中 4 与 1-b 属公共契约与高风险面，若选择需一并给出扩权。

未裁决前，**实现保持现状**：take 层继续零生产调用方，不新增迁移，不接线。
任何在裁决前把 take 接入回合交付的实现，都等于替架构师做了上面第 1 项决定。

本 ADR 不授权任何绕过上述裁决的改动。
