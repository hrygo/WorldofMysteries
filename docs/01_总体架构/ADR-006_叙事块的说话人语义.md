# ADR-006：叙事块携带说话人语义

> **状态**：待裁决（提案；供人类架构师与 AGT-ARB 评审）  
> **日期**：2026-10-01  
> **职责**：人类架构师负责架构裁决；AGT-ARB 维护决策与契约边界  
> **作用范围**：NarrativeBlock 契约、Context Compiler 投影、发布层、封存边界、按段交付  
> **前置文档**：[ADR-005](ADR-005_音色供给与铸造_v1.0.md)、[ADR-002](ADR-002_数据架构.md)  
> **语态约定**：第 2–4 节以终态事实语态定义系统行为；第 1 节记录当前证据，第 5 节记录决策状态（已裁决与仍待决定分列）。

---

## 1. 背景与证据边界

ADR-005 要求「按身份逐段配音」。该要求当前**无法满足**，原因不是供给链缺能力，而是已提交状态不携带说话人语义。两个表面无关的症状同源。

2026-10-01 的本仓静态复核确认以下事实：

| 证据 | 当前结论 | 对决策的约束 |
|:---|:---|:---|
| `engine/application/narrative_publication.py` | 每个 NarrativeBlock 恒为「一段 narration + 一段 protagonist 的 character」；`NarrativeCandidate` 只有 `narration` 与 `speech` 两个文本字段，docstring 明写「The speaker is intentionally absent: only the trusted committed source may bind a character segment」 | 模型不得自报说话人，这条锁正确，必须保留 |
| 同上 · `CommittedNarrativeSource` | 只有 `protagonist_id` 与一段 `disclosed_facts` 字符串，**没有任何「在场角色」概念** | 可信源手里没有第二个可绑定的身份 |
| `engine/application/speech_unit.py` | 封存边界显式拒绝无 speaker 的 narration（`non_character_segment_cannot_be_sealed`），并注明「在叙事块携带显式旁白身份之前，不允许调用方指定一个」 | 这是刻意设计而非疏漏；旁白不可配音是**契约缺字段**，不是代码 bug |
| `engine/infrastructure/migrations/` | 世界侧只有 `turn_character_changes`（本回合状态变更），**无场景在场角色名单** | 「在场」不能由「状态变了」近似，否则语义将永久错位且难以拆改 |
| `contracts/schemas/narrative_block.schema.json` | `segments` 已是数组，`type` 枚举含 `narration`/`character`/`transition`，每段带 `speaker_id` 与 `speech_intent` | 契约层**已支持多数说话人**，限制纯在生产端 |
| 本仓实测（`scratch/probe_shipped_audio.py`） | 连续五轮共 6 段，`type == "character"` 的段为 **0**；每轮返回 `narrative_has_no_character_segment` | 旁白不可达、NPC 不可达，是同一根因的两个表现 |

本次没有服务调用、人工听审或真实联调。上述结论全部来自源码与本仓测试。

## 2. 问题陈述

封存边界要确认「这段话的 speaker 与被绑定声音的 presentation_identity 是同一个人」，才能防止客户端或调用方替角色选声。`NarrativeBlock` 的 narration 段没有 `speaker_id`，于是这项确认对旁白**无从做起**——边界只能拒绝，而不是错误地放行。

NPC 则是另一面：发布层只会产出主角的 character 段，因为可信源没有「本回合谁在场」这个事实可供绑定。供给链已经能在缺声时自动起铸（ADR-005 D 系列），但它只能对**已经被发布出来**的段起作用；世界再大，可被发现的需求只有一个身份。

两者都需要同一件事：**已提交状态必须携带说话人语义**。

## 3. 决策

### D1 · 旁白身份由可信源写入，不由调用方选择

NarrativeBlock 的 narration 段携带 `speaker_id`，其值由发布层从可信源导出，遵循既有旁白 slug。封存边界对「narration 段缺少 `speaker_id`」继续拒绝（`speakerless_segment_requires_narrator_policy`）；新增的是**合法的旁白身份可以通过**，而不是放宽该检查。

`voice_binding_resolver.NARRATOR_IDENTITY` 与目录中旁白设计的 `presentation_identity` 逐字一致，二者共用同一 slug，不允许各写一份。

### D2 · 在场角色是可信源的显式事实

在场角色是**世界侧的事实**，不是发布时现算出来的。场景持久化自己有哪些角色在场；`CommittedNarrativeSource` 读取该事实，Context Compiler 再从**已授权上下文**投影出本回合可知的子集，遵守不变量 6（零知识越界）与不变量 7（语义授权先行）：不在本回合授权范围内的角色不得进入该集合，因此也不得获得台词。

这条决定了音色供给的自主程度。供给触发器在缺声时为**实际缺声音的那个 scope** 起铸，这一步早已自动；它之所以至今只见过一个身份，是因为发布层每块只产出一个角色段，而可信源手里没有第二个可绑定的身份。在场名单由世界自己携带之后，「谁在场景里」不再需要任何人点名：新增角色进入场景即进入名册，首次开口即缺声，缺声即起铸，全过程无需调用方指定。

该集合**不以 `character_deltas` 近似**。`character_deltas` 表达「本回合状态发生变化的角色」，与「本回合在场的角色」不等价：一个只在别处被提及的角色会因此获得台词机会，而一个沉默站场的 NPC 拿不到声音。用错误语义换速度，会把「在场」永久绑在状态变更上。

在场名单的**投影口径**由实现方案确定，但须满足两条：它只收窄、不扩充世界侧记录的事实；且它不因表达层重试而变化，否则同一段文本的两次发布会得到不同的可发声集合。

在场名单的来源已经落定：`StoryState.scene.active_character_ids` 是世界侧持久化的事实，开局即种下，场次增减由 `StoryDelta.active_character_ids_add` / `active_character_ids_remove` 逐回合提交。可发声名册是它的收窄，收窄规则见 [D5](#d5--在场不等于可发声)。

### D3 · 模型只提议对名册的引用，不指认身份

模型输出从「一段 speech」扩展为「若干行，每行携带一个对在场名册的引用」。发布层把引用解析为真实 `speaker_id`；解析不到的行连同该行一起被拒绝，**不得**退化为旁白或主角。

这保持 ADR-005 已确立的锁：模型不获得任何身份授权，它只能在一个已经授权过的集合里指位置。

### D4 · 逐段交付是契约形状，不是实现细节

`TurnDeliveryView` 当前只承载单个 `speech_unit_id` 与 `render_recipe`，因此一回合只能交付一个人的声音。验收标准 1 要求「按身份逐段配音」，故该视图必须扩展为批次形态。

批次内**逐段独立**：每段各自绑定、各自封存、各自交付；一段缺声不否决同批其他段，缺声段按 ADR-005 回退为字幕并显示明确状态。该行为复用已在单段路径验证过的静默供给触发器，缺哪个 scope 就为哪个 scope 起铸。

### D5 · 在场不等于可发声

在场与发声是两个事实：来源不同，理由不同，因此分两层记录。合成一层之后，其中一个会悄悄顶替另一个，而顶替在测试里看不出来。

`StoryState.scene.active_character_ids` 记录**在场**——谁在物理上处于这个场景。它是世界事实，主角在其中，与其他角色无异。

可发声名册是在场名册**再收窄**一层的结果，收窄有两条理由，必须分开：

1. **产品设定**：玩家代入的角色不铸色。主角始终在场，但永不进入可发声名册——玩家用自己的声音说话，系统不为其铸造音色。
2. **语义授权**：不在本回合授权范围内的角色不得进入（不变量 6、不变量 7）。

两条不得合并为一条。合并后，「因为玩家有自己的声音所以不铸」与「因为本回合无权知道此人」会共用同一个开关，日后改动其一将静默改动其二——而这两者在业务上毫无关系。

排除只发生在可发声名册这一层。把主角一并从 `active_character_ids` 删除是伪造世界事实：世界侧会声称主角不在场，并连带使依赖在场名册的其余判断一并失真。

## 4. 影响与边界

**解锁**：ADR-005 验收标准 1 的「按身份逐段配音」；旁白与 NPC 进入供给链；`NARRATOR_IDENTITY` 从当前不可达变为可达。

**纠正（2026-10-01）**：本 ADR 初稿称「在场角色集合是表达层事实，不推进世界 revision」。实现阶段查明该判断有误，并已按事实落定：在场名册是**世界事实**，由 `StoryState.scene.active_character_ids` 持久化，随 `StoryDelta` 逐回合增减，与 `story_revision` 同步推进。属于表现层的是它之上的**收窄结果**——可发声名册——而收窄不写回世界。两者不可混为一谈：把世界事实说成表现层，会让人以为它可以在不提交世界的情况下被改写。

**不改变**：模型的说话人授权边界（不变量 6/7 不变，仍为零）；已提交事实与表现数据的分离；换声仅影响未来片段（绑定键含 worldline 与 presentation identity，显式替换语义不变）。

**代价**：改动横跨四个角色——`contracts/schemas/`（AGT-ARB）、`engine/application/` 与 `engine/infrastructure/`（AGT-AI / AGT-DATA / AGT-VOICE）、`macos-app/` DTO 与播放（AGT-MAC）。需一次完整门禁与契约版本升级。

**与外部阻塞的关系（2026-10-01 更新）**：SpeechRail [#126](https://github.com/hrygo/SpeechRail/issues/126) 已修复并实测通过——真实 TTS + 真实 ASR 下，四个克隆音色的输出门禁由 `reject / transcript_match 0.76` 变为 `pass / 1.0`，六条探针全满分。根因与该 issue 初稿的归因不同：主犯是 `pause_markers` 探针中的 `……`（NFKC 改写为 `......`，而 `.` 是保留语义符号，25 字参考凭空多出 6 个字符误差），`22.5℃` 仅为次犯。

但 `production_ready` 仍为 false，阻塞点已转移：合成证据绑定要求运行器上报模型运行期身份（`rt_` 前缀 + 64 位十六进制），当前取值为空，证据因而被判为 `model_runtime_identity_unknown` 而无法绑定。**该阻塞与本 ADR 无关，且不因本 ADR 完成而解除。**

### 4.1 接线约束（2026-10-01 实现阶段查明）

以下六条是落地 D2 时才暴露的事实。它们不是实现细节：任何一条被忽略，得到的都是一个**看起来能跑、实际会错**的系统。

**一、名册必须走授权 evidence，不能裸读。** 不变量 7 要求 Context Compiler 裁决「有资格获知什么」。把名册当作一个普通读取直接塞进提示，等于绕过该裁决——这正是本 ADR 一开始要防的事。可复用的机制已经存在：`AuthorizedContextSource` 记录 `source_id` / `source_revision` / `fingerprint`，而 binding 的 manifest 正由 `PromptPlan.ordered_evidence` 生成。把名册做成一条 evidence，一次得到三件事：授权由构造保证、按回合冻结、指纹漂移时 fail closed 而非静默用错。

**二、绝不读「最新」场景状态。** `post_commit_handlers._load_committed_turn` 已有的约束是「只通过冻结的 turn 身份解析」。原因是 `story_state_json` 只保存**当前**状态、不保留历史：回合 N 发布时读到的是此刻的名册，若其后有角色进出场，已发布那一段的说话人就会错配——而系统不会报错，它只是把错的配音发了出去。

**三、按回合冻结的强度尚未决定，但天平已经倾斜。** 指纹漂移即 fail closed 复用现有 `context_stale`，零迁移；代价是名册变化后的重试被拒绝。更彻底的做法是按回合持久化名册快照，属 `engine/infrastructure/migrations/` 高风险面。

> **2026-10-01 实现阶段更新。** 名册已作为独立 evidence 落地（`scene_roster`，见 §4.2），指纹覆盖名册内容，因此**冻结强度不再是一个开放设计选项，而是这一实现选择的直接后果**：名册一变，指纹即漂移，绑定旧名册的那次调用必然 fail closed。要换取「名册变化后重试仍可用」，就得再引入按回合的持久化快照——那不是本 ADR 的细化，是一项独立的高风险迁移。§5.2 中的待决项据此重述。

**四、D5 不能在发布层单独生效，必须先有 D3。** `CommittedNarrativeService._block` 目前恒产出一个 `speaker_id = protagonist_id` 的 character 段，因为模型的唯一输出形状是一段无归属的 `speech`，发布层没有第二个可绑定的身份。D5 裁决「主角不铸色」之后，这个段本身就是错的；但**先执行 D5 会让叙事发布整片失败**——profile 还带着 `properties.speech.minLength = 1` 强制 speech 非空，主角段一旦被拒，每一回合都发不出去。正确顺序是 D3 先落地（模型按名册逐行提议），发布层随之按名册绑定，D5 才随之生效。

**五、evidence 的组装跨角色。** plan 由 `AuthorizedLiveExecution` → `coordinator.prepare(call)` 组装，evidence 来自世界侧读取。因此名册接线不是一片：世界侧 evidence 组装在 AGT-DATA 管辖的 `engine/infrastructure/`，编译器与两处生产构造点在 AGT-AI。把它硬塞进一片会同时踩两个角色的写范围；而只做「把名册读进来传下去」而不做授权 evidence，比不做更糟——那正是本节第一条禁止的 fail-open 形态。

**六、名册不能搭载共享 `checkpoint`。** `checkpoint` 被 `character_reasoner`、`story_director`、`observation_narrator` 一并消费。把名册折进 `checkpoint`，等于让每一个角色都看见「房间里还有谁」——违反不变量 6，且这种泄露不会报错，只会让模型在不该知道的事情上表现出知道。因此名册是独立 kind，`_ALLOWED_KINDS` 只对 `narrative_compiler` 开放。

### 4.2 名册接线现状（2026-10-01）

链路第 1—4 步已合入 `main`：

| 步骤 | 内容 | 角色 |
|:---|:---|:---|
| 1 | `StoryDelta` 新增 `active_character_ids_add` / `_remove`，reducer 消费——名册从开局冻结变为可变 | AGT-ARB / AGT-DOM |
| 2 | `disclosed_castable_roster()`：从场景在场集合投影出可发声名册 | AGT-AI |
| 3 | `_ALLOWED_KINDS["narrative_compiler"]` 单独开放 `scene_roster` | AGT-AI |
| 4 | `SQLiteGameplayContextRepository._project_scene_roster()`：为叙事编译投影该 evidence | AGT-DATA |

第 4 步确立的两条边界，均有测试钉住：

- **可信侧与模型侧分离。** `content` 带 canonical id（发布层据此绑定音色），`model_content` 只带公开 label（`character_display_names` 白名单）。白名单缺失或畸形一律按空表处理——最坏结果是无人可发声，而不是把 canonical id 端给模型。
- **消费者唯一。** 遍历 `GameplayMode` 的测试断言：只有 `narrative_compilation` 得到 `scene_roster`，`character_reasoning` 仍只得到 `checkpoint`，`advice_interpretation` 仍只得到 `observation`。

链路第 5 步**只完成了一半**，D3 与 D5 已合入：

| 步骤 | 内容 | 状态 |
|:---|:---|:---|
| 5a | 随发布路径（`CommittedNarrativeSource`）传递名册 | ✅ VF-82A |
| 5b | 延迟作业在 COMMIT 时取名册 | ❌ 未做，见下|
| D3 | 模型按名册逐行提议（profile `wom-live-narrative-v3`，`{narration, lines}`） | ✅ VF-83C |
| D3' | 发布层按名册逐行绑定说话人 | ✅ VF-83B |
| D5 | 主角不铸色随发布层绑定生效；`speech` 迁移缝已删除 | ✅ VF-83D |
| D4 | 一块内多段各自配音的批次化交付 | ❌ 未做 |

**第 5b 步为什么仍未做**：延迟作业（`post_commit_handlers`）不能安全取名册——既有测试
`test_live_narrative_rebuild_uses_the_job_delta_after_later_session_changes`
以 `assert story.latest_session_reads == 0` 明文禁止读取最新会话状态，任何在延迟作业里
读名册的实现都会把冻结约束降级为「尽力而为」。正确解法是**在 COMMIT 时把名册冻结进
`PostCommitWorkSource`**（跨 AGT-AI / AGT-DATA，需拆片），不是放宽该约束。

第 5b 步未做的**可观测后果**：`post_commit_handlers.py` 构造的 source 不带名册，
`castable_character_labels is None`，而 VF-83C 的 schema 收窄使该路径的 `lines` 只能是
空数组——因此**延迟作业发布的叙事块只有旁白、没有角色台词**。这不是新缺陷，而是
「名册未冻结」第一次有了可见症状；补齐第 5b 步即可恢复。

**D4 是验收标准 1「按身份逐段配音」当前最后的缺口**：`story_runtime.py` 的交付协调器
目前只取 `candidates[0]`，即一块里只有**第一个**角色段会被配音。名册已经能给出多个
说话人，交付层却仍然只发一条声音。D4 需要把 `TurnDeliveryView` 从单条
（`speech_unit_id` / `spoken_text` / `render_recipe`）扩成按段有序的批次，其中缺声段
单独标注状态而**不牵连其他段**（验收标准 3）。该改动跨 `contracts/`（AGT-ARB）、
`engine/`（AGT-AI）与 `macos-app/`（AGT-MAC），须拆片交付。

## 5. 决策状态

### 5.1 已裁决

1. **主角不铸色（2026-10-01，人类架构师）。** 玩家代入的角色不铸色——主角始终在场，但不进入可发声名册，玩家的声音不来自系统铸造的音色。规则见 [D5](#d5--在场不等于可发声)。此项此前的反复讨论源于目录里没有主角、而发布层每块只产出一个角色段，使「主角要不要单独开一条路」看起来像个架构选择；D5 把它还原成产品设定，并明确它与语义授权是两条独立的收窄理由。
2. **在场角色集合的投影口径。** 取场景的 `StoryState.scene.active_character_ids`，而非队伍或当前镜头——「在场」是场景事实，队伍是叙事约定，用后者会把「谁跟着走」与「谁在这个房间里」混为一谈。可发声名册在该集合上按 [D5](#d5--在场不等于可发声) 再收窄一层：排除主角，另排除本回合未获授权者。
3. **`scope_ref` 的授权范围（2026-10-01，人类架构师）。** 本部署铸造的音色**全部由文字
   设计合成，不取样任何真人声音，仅用于本项目用户世界的原创角色**。该范围必须由部署侧
   显式声明（`WOM_FOUNDRY_SCOPE_REF`），仓库不内置默认值——内置一个未经授予的权利主张，
   会让每一条铸造证据都带上无人授予的权利声明，而缺声明时直接无铸造能力是正确失败。
   同一部署下的 `WOM_FOUNDRY_MODEL_ID` 取 SpeechRail 模型目录键 `speechrail/qwen3-tts`
   （`variant=custom_voice`，与该模型目录项一致），与 `DEFAULT_VARIANT` 一致，无需覆盖。
4. **角色公开名一律中文。** 世界内所有人物（含用户世界原创角色）的公开名使用廷根式中文
   虚构名，不出现现实语族的音译名或英文名（`Jonathan` 一类写法作废）。既有的
   「不贴现实民族标签」纪律对**读音**同样生效：名字要能被念出来，也要听起来属于此地。
