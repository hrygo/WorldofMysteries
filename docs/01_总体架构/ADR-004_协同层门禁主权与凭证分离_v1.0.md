# ADR-004：协同层门禁主权、凭证分离与工作区运行时隔离

> **状态**：Accepted（已实施并本地验证）
> **日期**：2026-09-16
> **决策者**：人类架构师（授权）· AGT-ARB（实施）
> **作用范围**：HACF 协同层（`scripts/`、`.hacf/`、`contracts/engineering/`、`.github/`、`.agents/`）
> **前置文档**：[`高效人机协同研发体系实施方案_v1.1.md`](../03_工程规范/高效人机协同研发体系实施方案_v1.1.md)

---

## 1. 背景与问题

HACF 2.0（v1.0 实施方案）确立了「任务胶囊 + 事务型 Worktree + 本地三阶段门禁 + 机器签名」模型，
方向正确，但经外部专家评审与本机实测复核，发现 6 处「看起来工业化、实际缺一层」的缺口：

| 编号 | 缺口 | 实测证据（改动前） |
|:---|:---|:---|
| G1 | 共享 `.venv` 把隔离工作区重新耦合 | `collab_pipeline.py` 将 `engine/.venv` 软链到主仓；实测 uv 0.12.15 的 editable 安装把 `.pth` 写成**项目根绝对路径**，worktree 内 `uv run` 会重写该共享环境 |
| G2 | 验收命令由胶囊携带，可被任务自行改写 | `capsule["verification_commands"]` 直接执行；范围审计显式跳过 `.agents/capsules/` |
| G3 | `forbidden_patterns` 是死字段 | 仅被写入胶囊与打印，`verify` 与 CI 均无判定点 |
| G4 | 凭证与契约混为一体，且回写契约 | `verify` 向胶囊写入 `attestation`，状态跃迁 `VERIFIED` |
| G5 | 「sha256 防伪签名」名不副实 | 签名为 `sha256(task_id + timestamp)[:16]`，不含任何内容摘要；CI 仅检查字段存在 |
| G6 | 展示层混入证据层 | PR 报告卡硬编码 `✅ PASSED`，且 reporter 无 `needs:` 依赖，CI 全红时仍可显示全绿 |

---

## 2. 决策

### D1 · 工作区独立环境 + 共享依赖缓存
每个 Worktree 通过 `uv sync --locked --extra dev` 创建**独立** `engine/.venv`，只共享 uv 全局缓存。
禁止软链主仓 venv。资源命名空间（`TMPDIR` / SPM scratch / 测试库目录 / IPC socket / 日志目录 / 端口段）
由 `.hacf/workspace.json` 租约分配 —— 源码隔离由 `git worktree` 提供，运行时隔离由租约提供。

### D2 · 门禁主权（Gate Sovereignty）
验收命令移出胶囊，固化于受保护的 `.hacf/gates/*.json`，摘要记录于 `.hacf/gates/registry.json`。
胶囊只携带 `gates.profile` 与 `gates.profile_digest`；`scripts/gate_runner.sh` 退化为薄封装。
摘要链：`capsule.profile_digest == registry.sha256 == sha256(profile file)`；
CI 以**目标分支（受保护 main）**的 registry 为权威 —— PR 内同时改写 profile 与 registry 无法自证通过。

### D3 · 契约与凭证分离
胶囊是不可变任务契约（`contracts/engineering/task_capsule.schema.json`），`verify` **不再回写胶囊**。
执行结果单独产出 `Work Receipt`，合入授权由 `Integration Receipt` 承担，落盘于 `.agents/receipts/<TASK_ID>/<head_sha>.json`。
rebase 后 commit SHA 变化 ⇒ 旧凭单不再是有效合入凭证，必须重新出单。

### D4 · 摘要口径诚实化
所有凭证统一表述为**可复算内容摘要（digest-recorded receipt）**，不再宣称密码学签名。
凭单绑定 `capsule_digest` / `base_commit` / `head_commit` / `target_sha` / `gate_profile_digest` /
工具链摘要 / 逐 stage 退出码 / 原始日志摘要 / runner 身份 / 时间区间。
抗伪造能力由受保护分支 + CODEOWNERS 评审 + CI 复算共同承担。

### D5 · 边界四分类与仲裁扩权
范围判定分为 `read` / `write` / `forbidden` / `privileged` 四类；
仅可仲裁扩权的面（`contracts/`、`.hacf/`、`.github/`、`engine/**/migrations/`）对非 `AGT-ARB` 角色
一律要求胶囊内显式 `privileged_grants`，否则返回 `SCOPE_ESCALATION_REQUIRED`。
`forbidden` 变为真实拦截点。高风险面被触碰时 `risk_class` 至少为 `high`。

### D6 · 证据层与展示层分离
`generate_pr_report.py` 只复述仓库内凭单的真实记录，移除硬编码通过状态；
门禁权威结论仅来自 CI required checks（`ci.yml` 三阶段 + `capsule-audit.yml` 证据审计）。
本地原始日志仅作为本地调试产物（`.log` 不入库），入库的是其摘要。

### D7 · 研发编排协议独立 namespace
新增 `contracts/engineering/`（`task_capsule` / `work_receipt` / `gate_profile`），
产品领域契约保持 `contracts/schemas/`（27 个）与 `contracts/protocol/`（1 个）不变。
研发协作协议与产品世界协议**分开版本化**，避免把 `Agent task / CI receipt` 与
`WorldEvent / ActionIntent / Episode` 混为同一类 Contract。

### D8 · 风险自适应门禁
新增 `risk_class`（low/medium/high/privileged）与按角色绑定的门禁档案
（`DOMAIN_P0` / `DATA_KERNEL_P0` / `AI_GATEWAY_P0` / `VOICE_P0` / `MACOS_APP_P0` / `FULL_P0`）。
集成阶段固定使用 `FULL_P0`，并在合入前记录 `expected_main_sha`、合入时做 compare-and-swap 复核、
合入后执行 post-merge smoke；任一环节失败即拒绝或报警。

## 3. 未采纳项（含理由）

| 建议 | 处置 | 理由 |
|:---|:---|:---|
| 将产品 `deployment target` 从 macOS 26+ 下调统一为 macOS 15+ | **驳回** | 事实错误：`project.pbxproj` 为 `MACOSX_DEPLOYMENT_TARGET = 26.6.2`，Phase 0 交付物已记录「macOS 26+ 平台基线全面对齐」，且根级约定禁止保留旧系统兼容分支 |
| 用完整 GitHub Merge Queue 替代本地 ff 合入 | **暂不采纳** | `--ff-only` 本质已是乐观 CAS（main 前进则失败而非静默错合）；本轮以 `expected_main_sha` + post-merge smoke 补齐真实缺口，避免引入外部依赖 |
| 由胶囊承载 `verification_commands` | **驳回（G2）** | 任务不得自证门禁；命令主权在受保护档案 |
| 保留共享 `.venv` 以省磁盘 | **驳回（G1）** | 环境写入竞争（`.pth` 重写）跨工作区污染，磁盘收益不值得正确性代价 |

## 4. 影响与回退

**影响**：
- `.agents/capsules/*.json` 结构变更（旧格式胶囊需 `pack` 重新生成；旧格式将被审计拒绝）；
- `contracts/schemas/task_capsule.schema.json` 迁出至 `contracts/engineering/`；
- CI 新增门禁档案校验与证据审计，代码类 PR 无胶囊 + 无凭单将被阻断；
- `.github/` 由「范围审计豁免」改为「高风险面」。

**回退**：本 ADR 的改动集中在 `scripts/`、`.hacf/`、`contracts/`、`.github/`、`.agents/`、文档与 `.gitignore`；
按文件 `git checkout` 即可回到 HACF 2.0 行为（`contracts/schemas/task_capsule.schema.json` 可原样恢复）。
回退会同时失去 G1–G6 的防护，需经人类架构师确认。

## 5. 验证证据（2026-09-16 实测）

| 验证项 | 命令 | 结果 |
|:---|:---|:---|
| 全量三阶段门禁 | `bash scripts/gate_runner.sh` | 3/3 stage passed |
| Python 测试（含新增治理测试） | `uv run --locked --extra dev pytest -q` | 38 passed（原 25 + 新增 13） |
| 门禁档案摘要一致性 | `python3 scripts/gate_profile.py check` | 6/6 profile 摘要匹配 |
| 门禁档案篡改拒绝 | `pytest -k gate_profile_tampering` | 覆盖档案未更新 registry 时被拒绝执行 |
| Worktree 独立环境 | `collab_pipeline.py start` + 检查 `.pth` | 工作区 venv 的 editable 路径指向**本工作区**，主仓环境未被触碰 |
| 范围越界拦截 | 在 worktree 注入 `engine/domain/*.py` 后 `verify`（AGT-MAC） | `SCOPE BREACH` + 退出码 1 + 失败凭单 |
| 契约不被回写 | 同一胶囊 verify 前后 `capsule_digest` | 摘要不变，无 `attestation` 字段写入 |
| 集成闭环 | `collab_pipeline.py integrate --auto-clean` | 门禁 → CAS → ff 合入 → post-merge smoke → Integration Receipt → 工作区与分支清理 |

**已知局限**：CAS 拒绝分支（main 在门禁与合入之间前进）本轮未在真实并发下触发，仅经代码审查确认；
`stale_context` 判定基于目标分支 SHA 变化，尚未覆盖「胶囊生成后目标分支多次前进」的累积情形。
