#### V12 附：互动资源竞争已实测（2026-10-02）

交付方案要求「重负载语音工作只在互动空闲窗口启动」，且「并行优化以测量为依据」。
此前**没有任何测量支撑这条策略**，它建立在直觉上。2026-10-02 用真实本机服务补上：

工具：`scripts/voice_contention_probe.py`（只读真实服务，不发布任何内容）。

为什么这个配对才是「互动」：oMLX 与 SpeechRail **共用同一份
`Qwen3-TTS-12Hz-1.7B` bf16 权重**、同一台 Apple Silicon 设备。
剧情回合不是无关的后台任务，它是同一块加速器的另一个占用者。

实测（每场景 3 次，中位；SpeechRail `/v1/realtime` + oMLX
`KAT-Coder-V2.5-Dev-OptiQ-4bit` 真实推理在途）：

| 指标 | 空闲 | 剧情推理在途 | 变化 |
|:---|:---|:---|:---|
| RTF（渲染耗时 / 音频时长） | 0.253 | 0.403–0.415 | **1.59–1.64x** |
| TTFC（发出请求到首块音频） | 0.026 s | 0.061–0.062 s | 2.35x |
| 并发时 LLM 吞吐 | — | 100.6–106.3 tok/s | — |

**结论**：

1. **策略成立，且现在有数字**：剧情回合在途时配音渲染慢约 1.6 倍。这**证实**
    重负载语音工作（预取、铸造、批量渲染）应避开互动窗口，而不是并行化。
2. **交付路径不受影响**：即使并发，RTF 仍 < 1（渲染快于播放），
    TTFC 仅 61 毫秒——玩家感知不到。所以「文字先交付、音频后补」在竞争下依然成立，
    验收标准 3 的连续性不因竞争而受损。
3. **冷启动才是真正的大头**：首次渲染 TTFC 2.64 s、RTF 0.869，
    而热态 TTFC 0.025 s、RTF 0.243——**相差约 100 倍**。空闲窗口策略的主要收益
    来自避开冷启动，而非避开 CPU 竞争（纯 CPU 负载 2/4 进程仅使 RTF 上升 4%/9%）。

**本测量的边界（不得外推）**：单机、单模型配对、每场景 3 次；
未测铸造路径、多声线批次、长时间热节律与多机情形。它是筛查信号，不是认证。
按 ADR V03，机器结果不替代人工听审结论。

## 3. 绑定阻塞：根因已更正（2026-10-02 第二次核实）

> **本节此前判定「上游 SpeechRail 未上报 `model.runtime_revision`，属跨仓硬阻塞，
> 本仓无可修之处」。该结论错误，此处更正。** 下文 §3.1 保留当时的实测事实
> （事实本身没错），但**归因错了**：不是上游缺功能，而是**冷启动时 worker 通道尚未加载**。
> 正确表述与证据见 §3.1。

### 3.1 正确根因：能力快照依赖「通道是否恰好已加载」

SpeechRail **早已实现** `rt_` + 64 hex 的运行期身份机制
（`backends/model_identity.py:59 observed_runtime_revision`、
`:144 is_observed_runtime_revision`）。绑定被拒的真实链路是：

1. `application/capability_snapshot.py:175` —— 对 clone 模式声音，
   若 `binding_required and runtime_identity_status != "observed"`，
   判 `model_runtime_identity_unknown` → `production_ready=false`。
2. `runtime_identity_status` 由 `application/voice_validation_gate.py:126-139` 决定：
   取 `observed_runtime_revision_for_synthesizer(synthesizer, voice)`，
   即**向已加载的 worker 通道询问**；通道未加载则返回 `None`。
3. `backends/qwen3_tts.py:1102 runtime_revision_for_voice` —— 按 `profile.runtime_role`
   取 worker；`self._workers.get(role)` 为空即 `None`。

**所以「运行时身份未知」是「通道没加载」，不是「模型无法标识」。**

实测（2026-10-02，本机 `http://127.0.0.1:8201/v1`）：

| 时刻 | `wom-*`（clone，需 `tts_base` 通道） | 原因 |
|:---|:---|:---|
| 冷态（仅渲染过 `aiden`＝`tts_custom_voice` 通道） | `production_ready = false` | `model_runtime_identity_unknown` |
| 用 `wom-07f9f73eb66b112c` 渲染一次（加载 `tts_base`） | `production_ready = true` | `validated` |

通道加载后本仓适配器复核：`production_ready=false` 由 7 个降为 **2 个**，
5 个 `wom-*` 全部放行，且带 `voice_identity_assurance = content_addressed`
与正式 `voice_revision`（如 `vr_6d6ea61cebdf696e0484a61d709409e0`）。
剩余 2 个 `voice_clone_*` 的理由是 `synthesis_validation_not_run`——
**那是正确的拒绝**（这两个音色确实没做过合成验证），与运行时身份无关。

**这意味着验收标准 1/2 的硬阻塞并不存在**，本仓与上游都不需要为「补字段」改代码。

### 3.2 但仍有两个真问题

**其一，冷启动会复现。** 本机 `SPEECHRAIL_WORKER_IDLE_TIMEOUT_SECONDS=1800`
且 `SPEECHRAIL_WORKER_LAZY_LOAD=true`：通道闲置 30 分钟后卸载，
下次绑定会再次得到 `model_runtime_identity_unknown`。
能力快照是只读 GET，却把「通道是否恰好已加载」掺进了 `production_ready`——
**读路径不应依赖运行态偶然量**。这需要 SpeechRail 侧修复（能力快照前准备通道，
或让 `production_ready` 只反映证据有效性而非当前加载态）。

**其二，能力响应确实仍未上报运行期身份。**
`application/capability_snapshot.py:58 model_identity()` 把
`"runtime_revision": None` **写死**——即使 worker 已观测到身份，
`/v1/speechrail/capabilities` 也不会带上它。这与 §3.1 的观察一致，
是**独立于冷启动问题的第二个真实缺口**：本仓读 `voices[].model.runtime_revision`
永远得到 `None`。修复它仍需上游改动，但这是「补 reporting」，
不是「补能力」，风险与工作量都远小于此前的判断。


### 3.3 原判定依据的实测事实（2026-10-02 首次核实）

对本机 SpeechRail（`http://127.0.0.1:8201/v1`）实跑本仓适配器
`probe_audio_capabilities`，能力快照本身健康：

```
status = ready
assurance = effective_capabilities_v1
errors = ()
```

但快照内 **7 个声音 `production_ready = false`，理由一律为 `model_runtime_identity_unknown`**，
且其 `model.runtime_revision` 均为 `None`：

| 声音 ID | variant | `production_ready` | `runtime_revision` |
|:---|:---|:---|:---|
| `voice_clone_02dab1c17f084757af90c4cd45292c18` | base | false | `None` |
| `voice_clone_9bca8173ec6b417dbb52331f2060debc` | base | false | `None` |
| `wom-07f9f73eb66b112c` | base | false | `None` |
| `wom-3c13efe683f2888a` | base | false | `None` |
| `wom-77dd89eaa0dea140` | base | false | `None` |
| `wom-9ccb6af97c28642e` | base | false | `None` |
| `wom-d2888cc51194ee2e` | base | false | `None` |

对照组：9 个 `custom_voice` 声音 `production_ready = true`（理由 `validated`），
其 `catalog_revision` 为 `08b854525817066e04ef6b6430a3faa0eebd24d2`。
被拒的 base 变体其 `catalog_revision` 为 `73ae2cb59832ed1eb13c249e378b854cfc643131`。

即：**目录修订已知，运行时身份未知**。这正是 V01「带 pin 但缺合格证据的声音不能正式合成」
要拒绝的情形——本仓行为正确。

### 3.4 本仓侧无需改动（结论仍成立）

解析侧已正确：`engine/infrastructure/audio/capabilities.py` 的 `_parse_model_identity`
把 `runtime_revision` 读进 `model_runtime_revision` 字段。准入判定消费上游的
`production_ready`（`engine/application/voice_casting_policy.py`），
在上游如实回答「运行时身份未知」时**正确地 fail closed**。

这不是可以靠放宽本仓判定绕过的问题：放宽会让 V01/V11 的保证失效。

### 3.5 修好之后上游要做的（已缩小）

经 §3.1 更正，上游要做的只剩两件，且都比原判断轻：

1. **让 `production_ready` 不依赖通道加载态**（§3.2 其一）。当前一个只读 GET
   会因为 `tts_base` 通道恰好没加载而报告 5 个已发布且已验证的音色不可用。
   修法二选一：快照前准备通道；或让该判据只反映验证证据是否失效，
   把「当前未加载」表达为 `not_requested` 而非 `unknown`。
   **不得**简单放宽为 `true`——那会让 V01 的引用稳定性在跨进程重启后失效。
2. **让能力响应带上 `runtime_revision`**（§3.2 其二）。
   `capability_snapshot.py:58 model_identity()` 目前把它写死为 `None`，
   即使 worker 已观测到身份也不上报。这是纯 reporting 缺口：
   机制（`observed_runtime_revision`）已实现，只是没接进响应。

两件都修好后，本仓侧无需改动即可获得稳定可用的绑定路径。

### 3.6 契约依据与两个候选修法的代价（供上游裁决）

按 SpeechRail 仓库自身的规则「契约定义预期行为，实现偏离契约应报告为差异」，
本节给出该偏离的契约依据。`contracts/openapi.yaml:1293-1299` 把准入结果定义为：

> `voice_not_production_ready`（**no output-pass evidence bound to the current voice
> revision, artifact and tier**）
> `voice_validation_runtime_changed`（the worker runtime identity changed
> **between preparation and synthesis**）

按契约，`production_ready` 由**证据是否绑定当前 voice revision / artifact / tier** 决定，
运行期身份是**另一个**判据，且作用域是「preparation 与 synthesis 之间」。
**加载态不在契约语义内。**

而现实现（`capability_snapshot.py:175`）把运行期身份观测拉进快照判据，
使 `production_ready` 随「通道此刻是否恰好已加载」翻转——**这是对自家契约的偏离**。

| 候选修法 | 做法 | 代价 |
|:---|:---|:---|
| A · 快照前预热通道 | 构建快照前 `await active.tts_clone.prepare_voice(...)` | 保持现有保守语义，**不削弱任何保证**；但只读 GET 会触发模型加载，冷态首次探测约 +2.6 s（实测冷渲染 TTFC），且等于让惰性加载在每次能力探测时失效——与 `SPEECHRAIL_WORKER_LAZY_LOAD=true` 的设计意图相抵 |
| B · 按契约拆开判据 | `production_ready` 只看证据；运行期身份仅在合成准入时检查（即 `voice_validation_runtime_changed` 的本职） | 语义最贴契约、能力快照变纯只读；但**会削弱本仓准入**：本仓目前正是靠 SpeechRail 的 `production_ready` 获取运行期保证——本仓读到的 `voices[].model.runtime_revision` 恒为 `None`（§3.2 其二），拿不到第二重保证 |

**两个修法都要动上游的安全属性，故本轮不擅自实施。** 可确定的是：
A 是保守修复、B 是契约修复，二者对下游 WorldofMysteries 的影响方向相反
（A 保持现状语义、B 会让本仓准入变宽）。该取舍应由人类架构师裁决，
或先修本仓 §3.2 其二（让能力响应真正带上 `runtime_revision`），
使 B 的代价降为零——**那时 B 才是明显更优的选项**。

### 4.1 替换服务商：目标写了，实现没有，且此前未披露

价值目标写明「方案支持后续扩充人物与**替换服务商**」。2026-10-02 实测结论：
换成任何非 SpeechRail 服务商，**整个音色面关闭**——不是降级，是消失。

| provider_name | 渲染运行时 | 能力快照 | assurance |
|:---|:---|:---|:---|
| `speechrail` | 有 | （按探测结果） | — |
| `openai-compatible` | **None** | `not_applicable` | `not_applicable` |
| `elevenlabs` | **None** | `not_applicable` | `not_applicable` |

三处同形硬闸，全部按 provider 名字短路：

| 位置 | 后果 |
|:---|:---|
| `engine/infrastructure/audio/capabilities.py:443` | 非 SpeechRail 直接返回 `not_applicable`，不做能力探测 |
| `engine/infrastructure/story_runtime.py:673` | `_open_voice` 返回 `None`，无渲染运行时 |
| `engine/infrastructure/story_runtime.py:698` | `_open_foundry` 返回 `None`，铸造面不注册 |
| `engine/infrastructure/voice_binding_resolver.py:165` | `status != "ready"` 即抛 `voice_provider_not_ready`，绑定全拒 |

该行为已被测试固定（`tests/test_audio_adapter.py:435-436` 断言
`status == "not_applicable"`），因此不是偶发，而是当前设计。**在此之前
`docs/` 未任何位置声明这条限制。**

**它与两处既有表述冲突**：

- ADR-005 第 60 行要求「**不永久排斥具备相同保证的其他 provider 来源**」——
  当前实现按名字排斥，与该条相反。
- `AGENTS.md` 项目头声称「支持任意兼容第三方热拔插」——该声索目前不成立。

**为何本轮只披露不修复**：能力探测解析的是 SpeechRail 专有的
`/v1/speechrail/capabilities`，要支持替换需先定义**provider 中立的能力声明契约**
（新公共接口），属重大架构变更，按 `AGENTS.md` 须先出可评审方案而非顺手改。

**可评审方案（待架构评审，未实施）**：

1. 新增 provider 中立的能力快照契约，把 `voice_revision`、执行模型制品修订、
   可用性、保证等级表达为与厂商无关的字段；SpeechRail 现状作为**一种**映射实现，
   而非协议本身。
2. 三处硬闸改为按**能力是否已声明**判定，而非按 provider 名字。未声明即
   `not_applicable` 并继续 fail closed——**安全性不降**，只是让「已声明的其他
   provider」能走通。
3. 新 provider 接入只允许新增 adapter 映射，不得放宽准入规则；准入仍由
   `voice_casting_policy` 的同一套条件把关。
4. 回退：不引入契约时，上述行为与今日完全一致，故该变更可独立评审、独立回退。

### 5.1 更正：「扩充人物」对音色系统已交付（2026-10-02）

本报告 VF-96 曾把「支持后续扩充人物」判为**未交付**，理由是
`StoryInitializationService.initialize` 只接受 `golden_001`、初始名册写死在代码里。
**该判定判重了，此处更正。**

受限的只是**场景装载器**，不是音色系统。铸造供给触发取的是「谁的嘴动了」，
而不是「开局名册里有哪些人」：

| 环节 | 证据 | 含义 |
|:---|:---|:---|
| scope 来源 | `post_commit_handlers.py:483` `speaker_scope_for(session, item)`，逐已发布段落解析 | 谁发言，谁才有 scope |
| 设计意图 | `post_commit_handlers.py:469` 注释「scope *is* the speaker」 | 刻意不为「谁该有声音」做二次推断 |
| 台词来源 | `_published_lines(session_id, scope)` 读已发布叙事 | 只用玩家已看见的台词调音，未公开的不算 |
| 首次开口即触发 | `test_a_character_who_speaks_without_a_voice_starts_being_cast` | 无需任何人工配置即开铸造任务 |
| 无目录也能铸 | `test_a_character_nobody_wrote_a_brief_for_is_cast_from_what_they_said` | 没有铸造稿时从其台词合成 |
| 反复发言不重复开单 | `test_a_character_who_speaks_every_turn_opens_one_casting` | 幂等由 scope 派生 |
| 供给故障不影响回合 | `test_a_supply_chain_that_is_down_does_not_fail_the_turn` | 缺货不伪装成剧情失败 |

因此**新增角色只要开口，就会被铸造、复验、听审、发布并绑定**，不受开局名册约束。
场景名册的硬编码只影响「开局谁在场」，属场景编写范畴，且不影响 ADR-006 §4.2
第 5b 步的回放机制（新场景同样把 `initial_session` 存进 bootstrap）。

**仍然成立的真实限制**（范围比原判定窄得多）：无法装载 `golden_001` 之外的

## 6. 三项收尾的实测结果（2026-10-02 第三次核实）

### 6.1 ①铸造目录复用 —— 已交付并真机验证

**问题**：SpeechRail 对重复铸造回答 `409 Target voice ID already exists`，
且**不说是哪一条、不带任何证据**。此前每一次联调都死在这里，供给无法重复执行。

**做法**：供给在下铲之前先读目录，命中即绑定，不重复铸造。四个切片分属三个角色：

| 切片 | 角色 | 内容 | 合入 |
|---|---|---|---|
| VF-103 | AGT-DATA | 仓储具名门 `adopt_published_candidate` | `be516411` |
| VF-104 | AGT-AI | 端口 `find_published` + worker 铸造前先读 | `92b784dd` |
| VF-105 | AGT-VOICE | 适配器实现目录读取与幂等 `publish` | `203624f6` |
| VF-106 | AGT-AI | 联调测试同时走通两条路 | `875f71a3` |

三个设计决定值得记下，因为它们都是「看起来可以省掉、实际不能」的地方：

* **先读，而不是撞了 409 再读。** 409 不指向任何对象，事后反应只能再失败一次。
* **不复用候选阶梯，而是新增一扇具名的门。** `_require_forward_state` 拒绝跳级
  是对的：它拦的是「没铸造、没复验、没听审却声称已发布」。复用是它看不见的情形
  （三件事都发生过，只是不在这个任务里）。因此不把它变成规则例外，而是新增
  `adopt_published_candidate`，并保留其余全部约束：只接受恰在 `provisioning`
  的候选、绝不改绑已绑定上游身份的候选、同样受任务修订号 CAS 保护。
  通用 `update_candidate` 仍然拒绝这次跳级，并为此加了一条测试。
* **不折进 `create`。** `create` 靠原幂等键重放对账；一旦它开始「有时创建、
  有时采纳」，重放就可能绑到与首次那把不同的声音。

**真机实测**（`WOM_LIVE_SPEECHRAIL=1`，本机 `http://127.0.0.1:8201/v1`）：

* 全部 5 个角色复用既有已发布设计，零重复铸造，且各自 design id **互不相同**
  （排除串号）：旁白 `vd_a6b56d1c…`、victor-osborn `vd_38d91df6…`、
  ida-finch `vd_4a66708a…`、samuel-clark `vd_7af04eaa…`、george-hart `vd_683cb963…`。
* 另用一个未用过的 world（`WOM_LIVE_WORLD`，voice id 由 world id 派生）走通了
  **真正的铸造分支**，产出真实 WAV（reference 303 404 B、validation 372 524 B），
  `supply: "cast"`。两条分支都实测过，都不是「按代码推断应该行」。

**听审记录新增 `supply` 字段。** 采纳轮不产出任何新音频，记录里必须写明，
否则复核的人会以为这一轮也交出了待听音频，从而在一段这一轮根本没生成过的
录音上签字。采纳轮明写「本轮未渲染任何片段」并指向首次铸造它的那一轮。

### 6.2 ②`runtime_revision` 上报 —— 结论再次更正：无需改代码

§3.1 的归因（冷启动时通道未加载）经本轮独立核实**成立**；但 §3.2 列的两个
「真问题」，本轮得到与此前不同的结论：

**其一，冷启动：上游早已修好，本机跑的是陈旧构建。**
SpeechRail 提交 `d2de73fa`（2026-10-02 05:35，已在 `origin/main`，
「让 production_ready 不再随 TTS worker 占用翻转」）引入了
`voice_validation_gate._binding_from_recorded_runtime`：worker 不驻留时，

而本机运行的是 **2026-10-01 21:28 安装**的构建，
`site-packages/speechrail/application/voice_validation_gate.py` 中

旁证：`~/.speechrail/voice_validations.json` 里 6 条 wom 记录的
`model_runtime_revision` 与 `runtime_fingerprint` **全部规范且自洽**
（用上游 `_runtime_fingerprint` 复算，6/6 MATCH）——所以不是「上游没记录」，
是**部署版本陈旧**。

**处置**：改配置而非改代码（可回滚，`.env.bak-2026-10-02-vf`）：

`production_ready=true / validated`；本仓 `probe_audio_capabilities` 返回
`status=ready`。代价约 9 GB 常驻（3 个 worker 2.5+3.2+3.3 GB），

**其二，`model_identity()` 写死 `runtime_revision: None` 仍然为真，
但对本仓零影响。** 实测：暖态渲染后单读音色，`production_ready=true`
而 `model.runtime_revision=null`，二者并存，确认这是独立的陈述性缺口。
但本仓 `VoiceCapability.model_runtime_revision` **无任何代码消费**，
故修与不修对本仓行为**零影响**。彻底修需重建/重装 SpeechRail（其发版流程决定，
`speechrail install` 接受的是构建好的 wheel），属上游发版范畴，不在本轮范围。

> 判断跨服务行为前，应先比对**运行中的构建**与仓库 main
> （比对 `site-packages` 源码 + `git log -S`），而不是先读仓库源码推断运行态。

## 8. 严格盲测素材与三项实测更正（2026-10-02 第四次核实）

§7 补的是决策侧证据，标准 1 与标准 2 真正缺的那一项——**人耳在陌生台词上首次识别**——
仍然没有。本节记录为此准备好的素材，以及准备过程中查出的三件与既有结论不符的事。

### 8.1 盲测素材：同一句台词，五个声音

素材为 15 段音频 = **3 句台词 × 5 个声音**，分三组：

| 组 | 台词 | 片段 |
|:--|:---|:---|
| 1 | 雨从午夜开始下，一直没有停。 | `clip_01` – `clip_05` |
| 2 | 这条街到了夜里，就只剩下脚步声。 | `clip_06` – `clip_10` |
| 3 | 你要是想清楚了，明天早上再来找我。 | `clip_11` – `clip_15` |

两处刻意的设计：

* **每一句台词都由全部五个声音各说一遍**，组内顺序打乱。题材、措辞、
  语气因此**不携带任何身份信息**——听审人无法靠「这句像是医生会说的」缩小范围，
  只能靠声音本身判断。这是与既往「5 段同一句台词」最大的区别。
* **三句台词全部避开铸造时用过的参考文案**，因此识别必须跨过文本成立，
  同时构成标准 2 的跨文本复验。

全部 15 段由本机 SpeechRail `http://127.0.0.1:8201/v1` 用 `tts-1` 渲染，
24 kHz 单声道，时长 2.7–4.5 秒。

**本节不预设听审结果。** 素材已就绪，人工结论尚未产生，
因此 V03 仍是「有条件通过」、标准 1 仍带限制。

### 8.2 逐轴归因：缺口从「素材不足」变成「估计量不稳」

每个身份现在有 3 句**不同**台词，`scripts/voice_axis_attribution.py --min-sentences 3`
的「素材不足」判定已经通过。工具改报 `verdict: unstable`，理由是
「最接近配对」随帧选择改变的轴是**质感轴 spectral centroid**。

音高轴与语速轴在两种帧选择下**数值完全一致**，是稳的；只有质感轴不稳。
即 §5.3 那条「素材不足」的限制**已解除**，取而代之的是一个更窄的新限制：
现有估计量在质感轴上给出的排序不可信。

### 8.3 更正一：旁白不是「重铸过」，是同一段声音登记了两次

服务商目录里有两条 `narrator`：

| 声音 ID | 铸造时间 | `identity` 判定 |
|:---|:---|:---|
| `wom-d2888cc51194ee2e` | 2026-10-01 02:27 | `unevaluated` |
| `wom-9b9816bb30fad590` | 2026-10-02 08:16 | `pass` |

**两条的参考音频是同一段音频**：151,680 帧逐样本全等，sha256 相同。
用同一句台词分别渲染，差异也只有采样量级——F0 85.9 Hz vs 87.9 Hz，
spectral centroid 3234.9 Hz vs 3181.3 Hz，相差约 2%，
远小于身份之间的差距。

**机制**（`engine/application/voice_foundry.py:149`）：

    wom-<sha256(world_id | presentation_identity | persona_revision)[:16]>

`persona_revision` 取自 `persona-{design_revision}`。设计修订号一变，派生的
voice id 就变，于是 SpeechRail 不会返回 `409 Target voice ID already exists`，
而是**把同一段声音再登记一次**。旧的那条没有退役路径，至今仍是 `published`。

**对本轮的影响**：盲测选哪一版旁白都不影响答案键，因为两者实际是同一个声音。
**对标准 1 的影响**：「一个身份对应一个稳定声音」在服务商目录层面**没有被保证**
——目录允许同一身份名下存在多条已发布声音，而本仓的采纳路径（`find_published`）
只按传入的 voice id 精确匹配，不做同名去重。

### 8.4 更正二：两条探针音色并不存在，无需清理

本轮一度判定「两条集成探针音色仍是 `published`，等待清理」。**该判定不成立。**

实测：`GET /v1/voices` 返回 17 条声音，其中没有任何 `wom_probe_*`；
对 `wom_probe_f42fb1129d10` 调用删除，服务端回答 `voice_not_found`。

真实情况是：SpeechRail 的设计记录里仍有两条 `target_voice_id` 为 `wom_probe_*`、
`state` 为 `published` 的条目，**而它们指向的声音已经不存在**。
这是上游的陈旧元数据，不是活着的残留——**没有东西需要清理**。

**边界（不得外推为已发生的故障）**：本仓 `find_published`
（`engine/infrastructure/audio/voice_foundry_adapter.py:403-414`）
只按 `target_voice_id` 与 `state == "published"` 匹配，**不校验该声音是否仍存在**。
当前引擎只派生十六进制后缀的 id，结构上撞不到 `wom_probe_*` 这类 id，
所以这是**偶然免疫，不是设计防护**。

### 8.5 一条对「区分度又不是那么明显」的实测解释

三句台词同口径测量（自相关基频 + FFT 质心，取每身份中位数）：

| 身份 | F0 中位数 (Hz) | 逐句 F0 | 质心中位数 (Hz) |
|:---|---:|:---|---:|
+| victor-osborn | 87 | 85.1 / 87 / 94.5 | 2399.6 |
+| **narrator** | **105.3** | 87.9 / 105.3 / 110.9 | 3056.8 |
| samuel-clark | 129.7 | 127 / 129.7 / 167.8 | 2298 |
| george-hart | 135.6 | 126.3 / 135.6 / 135.6 | 2659.5 |
| ida-finch | 181.8 | 171.4 / 181.8 / 183.9 | 2881.4 |

**旁白与维克多是音高轴上最近的一对**（105 Hz vs 87 Hz），两者靠音色轴拉开
（质心 3057 Hz vs 2400 Hz）。而 §8.2 的归因工具判定的恰恰就是**音色轴不稳**。

这是对听审人「区分度不明显」的一个**可能**解释：最吃劲的那一对，
恰好落在唯一测不稳的轴上。**它是筛查信号，不是结论**——要坐实这一点，
需要 §8.1 的盲测结果与逐对混淆记录，二者都还没有产生。
