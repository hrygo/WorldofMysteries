#### V12 附：互动资源竞争已实测（2026-10-02）

交付方案要求「重负载语音工作只在互动空闲窗口启动」，且「并行优化以测量为依据」。
此前**没有任何测量支撑这条策略**，它建立在直觉上。2026-10-02 用真实本机服务补上：

工具：`scripts/voice_contention_probe.py`（只读真实服务，不发布任何内容）。

为什么这个配对才是「互动」：oMLX 与 SpeechRail **共用同一份
`Qwen3-TTS-12Hz-1.7B` bf16 权重**、同一台 Apple Silicon 设备。
剧情回合不是无关的后台任务，它是同一块加速器的另一个占用者。

实测（每场景 3 次，中位；SpeechRail `/v1/realtime` + oMLX
`KAT-Coder-V2.5-Dev-OptiQ-4bit` 真实推理在途）：

| 指标 | 空闲 | 剧情推理在途 | 变化 |
|:---|:---|:---|:---|
| RTF（渲染耗时 / 音频时长） | 0.253 | 0.403–0.415 | **1.59–1.64x** |
| TTFC（发出请求到首块音频） | 0.026 s | 0.061–0.062 s | 2.35x |
| 并发时 LLM 吞吐 | — | 100.6–106.3 tok/s | — |

**结论**：

1. **策略成立，且现在有数字**：剧情回合在途时配音渲染慢约 1.6 倍。这**证实**
    重负载语音工作（预取、铸造、批量渲染）应避开互动窗口，而不是并行化。
2. **交付路径不受影响**：即使并发，RTF 仍 < 1（渲染快于播放），
    TTFC 仅 61 毫秒——玩家感知不到。所以「文字先交付、音频后补」在竞争下依然成立，
    验收标准 3 的连续性不因竞争而受损。
3. **冷启动才是真正的大头**：首次渲染 TTFC 2.64 s、RTF 0.869，
    而热态 TTFC 0.025 s、RTF 0.243——**相差约 100 倍**。空闲窗口策略的主要收益
    来自避开冷启动，而非避开 CPU 竞争（纯 CPU 负载 2/4 进程仅使 RTF 上升 4%/9%）。

**本测量的边界（不得外推）**：单机、单模型配对、每场景 3 次；
未测铸造路径、多声线批次、长时间热节律与多机情形。它是筛查信号，不是认证。
按 ADR V03，机器结果不替代人工听审结论。

## 3. 阻塞项：上游 SpeechRail 未上报 `model.runtime_revision`

这是验收标准 1、2、6 端到端真实演示的**硬阻塞**，且**不在本仓**。

### 3.1 实测事实（2026-10-02）

对本机 SpeechRail（`http://127.0.0.1:8201/v1`）实跑本仓适配器
`probe_audio_capabilities`，能力快照本身健康：

```
status = ready
assurance = effective_capabilities_v1
errors = ()
```

但快照内 **7 个声音 `production_ready = false`，理由一律为 `model_runtime_identity_unknown`**，
且其 `model.runtime_revision` 均为 `None`：

| 声音 ID | variant | `production_ready` | `runtime_revision` |
|:---|:---|:---|:---|
| `voice_clone_02dab1c17f084757af90c4cd45292c18` | base | false | `None` |
| `voice_clone_9bca8173ec6b417dbb52331f2060debc` | base | false | `None` |
| `wom-07f9f73eb66b112c` | base | false | `None` |
| `wom-3c13efe683f2888a` | base | false | `None` |
| `wom-77dd89eaa0dea140` | base | false | `None` |
| `wom-9ccb6af97c28642e` | base | false | `None` |
| `wom-d2888cc51194ee2e` | base | false | `None` |

对照组：9 个 `custom_voice` 声音 `production_ready = true`（理由 `validated`），
其 `catalog_revision` 为 `08b854525817066e04ef6b6430a3faa0eebd24d2`。
被拒的 base 变体其 `catalog_revision` 为 `73ae2cb59832ed1eb13c249e378b854cfc643131`。

即：**目录修订已知，运行时身份未知**。这正是 V01「带 pin 但缺合格证据的声音不能正式合成」
要拒绝的情形——本仓行为正确。

### 3.2 本仓侧无需改动

解析侧已正确：`engine/infrastructure/audio/capabilities.py` 的 `_parse_model_identity`
把 `runtime_revision` 读进 `model_runtime_revision` 字段。准入判定消费上游的
`production_ready`（`engine/application/voice_casting_policy.py`），
在上游如实回答「运行时身份未知」时**正确地 fail closed**。

这不是可以靠放宽本仓判定绕过的问题：放宽会让 V01/V11 的保证失效。

### 3.3 需要上游做的事

SpeechRail 需在 `/v1/speechrail/capabilities` 的每个 `voices[].model` 上报
`runtime_revision`——按本仓既有契约，一个 `rt_` 前缀 + 64 位十六进制的稳定串。
该值必须标识**实际加载并用于渲染的模型制品**，而非目录项或配置别名：
同一目录项下模型被替换、量化变更或权重回滚时，`runtime_revision` 必须随之改变，
否则 V01 的引用稳定性在跨进程重启后不成立。

上游修复后，本仓侧无需改动即可恢复——本仓已在等这个字段。

### 4.1 替换服务商：目标写了，实现没有，且此前未披露

价值目标写明「方案支持后续扩充人物与**替换服务商**」。2026-10-02 实测结论：
换成任何非 SpeechRail 服务商，**整个音色面关闭**——不是降级，是消失。

| provider_name | 渲染运行时 | 能力快照 | assurance |
|:---|:---|:---|:---|
| `speechrail` | 有 | （按探测结果） | — |
| `openai-compatible` | **None** | `not_applicable` | `not_applicable` |
| `elevenlabs` | **None** | `not_applicable` | `not_applicable` |

三处同形硬闸，全部按 provider 名字短路：

| 位置 | 后果 |
|:---|:---|
| `engine/infrastructure/audio/capabilities.py:443` | 非 SpeechRail 直接返回 `not_applicable`，不做能力探测 |
| `engine/infrastructure/story_runtime.py:673` | `_open_voice` 返回 `None`，无渲染运行时 |
| `engine/infrastructure/story_runtime.py:698` | `_open_foundry` 返回 `None`，铸造面不注册 |
| `engine/infrastructure/voice_binding_resolver.py:165` | `status != "ready"` 即抛 `voice_provider_not_ready`，绑定全拒 |

该行为已被测试固定（`tests/test_audio_adapter.py:435-436` 断言
`status == "not_applicable"`），因此不是偶发，而是当前设计。**在此之前
`docs/` 未任何位置声明这条限制。**

**它与两处既有表述冲突**：

- ADR-005 第 60 行要求「**不永久排斥具备相同保证的其他 provider 来源**」——
  当前实现按名字排斥，与该条相反。
- `AGENTS.md` 项目头声称「支持任意兼容第三方热拔插」——该声索目前不成立。

**为何本轮只披露不修复**：能力探测解析的是 SpeechRail 专有的
`/v1/speechrail/capabilities`，要支持替换需先定义**provider 中立的能力声明契约**
（新公共接口），属重大架构变更，按 `AGENTS.md` 须先出可评审方案而非顺手改。

**可评审方案（待架构评审，未实施）**：

1. 新增 provider 中立的能力快照契约，把 `voice_revision`、执行模型制品修订、
   可用性、保证等级表达为与厂商无关的字段；SpeechRail 现状作为**一种**映射实现，
   而非协议本身。
2. 三处硬闸改为按**能力是否已声明**判定，而非按 provider 名字。未声明即
   `not_applicable` 并继续 fail closed——**安全性不降**，只是让「已声明的其他
   provider」能走通。
3. 新 provider 接入只允许新增 adapter 映射，不得放宽准入规则；准入仍由
   `voice_casting_policy` 的同一套条件把关。
4. 回退：不引入契约时，上述行为与今日完全一致，故该变更可独立评审、独立回退。

## 5. 结论

- **V01、V02、V04、V05、V06、V07、V08、V09、V10、V11：通过**（V04 含真实服务实测）。
- **V03：有条件通过**，两项限制已具名（再认非盲测、辨识余量小）。
- **V12：未验收**，并被一个跨仓阻塞硬性挡住。

### 5.1 更正：「扩充人物」对音色系统已交付（2026-10-02）

本报告 VF-96 曾把「支持后续扩充人物」判为**未交付**，理由是
`StoryInitializationService.initialize` 只接受 `golden_001`、初始名册写死在代码里。
**该判定判重了，此处更正。**

受限的只是**场景装载器**，不是音色系统。铸造供给触发取的是「谁的嘴动了」，
而不是「开局名册里有哪些人」：

| 环节 | 证据 | 含义 |
|:---|:---|:---|
| scope 来源 | `post_commit_handlers.py:483` `speaker_scope_for(session, item)`，逐已发布段落解析 | 谁发言，谁才有 scope |
| 设计意图 | `post_commit_handlers.py:469` 注释「scope *is* the speaker」 | 刻意不为「谁该有声音」做二次推断 |
| 台词来源 | `_published_lines(session_id, scope)` 读已发布叙事 | 只用玩家已看见的台词调音，未公开的不算 |
| 首次开口即触发 | `test_a_character_who_speaks_without_a_voice_starts_being_cast` | 无需任何人工配置即开铸造任务 |
| 无目录也能铸 | `test_a_character_nobody_wrote_a_brief_for_is_cast_from_what_they_said` | 没有铸造稿时从其台词合成 |
| 反复发言不重复开单 | `test_a_character_who_speaks_every_turn_opens_one_casting` | 幂等由 scope 派生 |
| 供给故障不影响回合 | `test_a_supply_chain_that_is_down_does_not_fail_the_turn` | 缺货不伪装成剧情失败 |

因此**新增角色只要开口，就会被铸造、复验、听审、发布并绑定**，不受开局名册约束。
场景名册的硬编码只影响「开局谁在场」，属场景编写范畴，且不影响 ADR-006 §4.2
第 5b 步的回放机制（新场景同样把 `initial_session` 存进 bootstrap）。

**仍然成立的真实限制**（范围比原判定窄得多）：无法装载 `golden_001` 之外的
新场景，也无法配置开局名册。这是场景编写能力的缺口，不是音色供给的缺口，
且不在本轮音色主线的验收范围内。
