## 0. 本包的读法与边界

**本包做什么**：把当前散落在 `docs/PROJECT_STATE.json` 的待裁决项收敛成可以直接勾选的问题，
每条给出已核实的事实、互斥候选及其代价、以及裁定前不得做的事。

**本包不做什么**：不做选择、不给推荐、不排序「哪个更值钱」。§8 只陈述依赖关系
（谁阻塞谁），那是从代码里读出来的因果，不是偏好。

**证据分级**（沿用验收报告 §0 的三态纪律）：

| 标记 | 含义 |
|:---|:---|
| 【实测】 | 在本包核对的 `origin/main` tip 上直接读源码或跑命令得到 |
| 【报告】 | 既有文档的记载，本包未重跑其验证 |
| 【新核实】 | 本包推翻了既有记载，并给出了反证 |

**基线**：本包所有【实测】均在 `origin/main` = `718c2f5c` 上取得。
`local main` 落后合入目标数百个提交，不可用于核实。

## 2. D-1 场景公开标签表

### 2.1 问题

是否建立一张按 `scene_id` 索引的公开场景标签表，取代今天唯一的
`story_initialization.SCENE_DISPLAY_NAME` 模块常量？

### 2.2 已核实的事实

1. 【实测】契约里没有任何场景名字段。`narrative_block.schema.json` 的段有
   `type` / `speaker_id` / `text` / `speech_intent`；块有 `scene_id`，无场景名。
2. 【实测】协议里**已有**所需形状：`story_session_control.schema.json` 的
   `scene_view` = `{id, location_id, display_name}`，且 `public_story_session_view.scene`
   已为**当前**场景填好（`story_public_view.py` 的 `PublicSceneView`）。
3. 【实测】全仓唯一的场景名是 `engine/application/story_initialization.py:35` 的
   `SCENE_DISPLAY_NAME = "哈维诊所 · 诊室"`，并由同文件 `_validate_presentation` 校验相等。
   它是按场景硬编码的常量，不是表。
4. 【实测】`PublicSceneView.id` 取自**实时** `story_state.scene.id`，而
   `display_name` 冻结在 bootstrap。二者今天恰好一致（场景从不切换），
   但形状允许它们漂移。
5. 【实测】`golden_001` 全目录 `scene_id` 零出现，各章 `scene_id` 今天全为 null，
   因此这一项当前不可观测。

### 2.3 候选与代价（不选）

| 候选 | 代价 | 解锁 |
|:---|:---|:---|
| **A. 建表**，按 `scene_id` 索引，随场景首次进入时登记公开标签 | 需要一处可信写入点（谁有权给新场景起公开名）+ 契约加性字段 + 投影与视图接线；与主角一半同构 | D-1 两处缺口全部落地 |
| **B. 不建表**，地点一半与叙述者披露都按「无可用公开标签」fail-closed（省略） | 最小改动；但 Story Book 永远没有地点，叙述者永远不知道场景变了——是真实的信息删除 | 无 |
| **C. 只做封面级展示**：把场景级单数名按「本书未出现多个场景」的前提印在封面，不逐章 | 最小可见收益；但前提一旦不成立就是错的，且要为这个前提写新的守卫 | 仅 Story Book 地点一半（且需接受前提风险） |

### 2.4 为什么它同时解锁两处

【实测】叙述者路径上，`engine/application/story_disclosure.py:49` 把
`story_delta.scene_id` 原样拼进披露文本（`场景转为：{scene_id}`），
经 `CommittedNarrativeSource.disclosed_facts` 进入
`engine/ai/live_turn_workers.py:741` 的模型调用载荷。
`engine/ai/` 全目录检索 `scene` 只命中一条注释与一句 speaker 提示词，
**这一行是叙述者获知场景的唯一途径**。

而同一个函数对**线索**是严格 fail-closed 的：没有公开标签就省略，
其 docstring 明写「emitting the id would turn a missing label into a disclosure」。
两处规则不一致，且已由
`verified_gaps.NARRATOR-SCENE-ID-DISCLOSURE` 记录、由三条治理守卫钉在代码上。

因此 D-1 的三个候选同时决定叙述者那条路径怎么处理：
选 A 则两处一起解决；选 B 则两处一起省略；选 C 则叙述者那条仍无解（叙述者需要逐场景标签，不能用封面级单数名）。

### 2.5 裁定前不得做

- 不得让视图或投影直接渲染 `scene_id` / `scene_id` 的任何变体（会同时构成零知识泄漏与事实错误）；
- 不得把 `SCENE_DISPLAY_NAME` 当作「当前场景名」继续复用——它是场景常量，不是查询函数。

## 3. D-2 旁白呈现策略与逐段交付

### 3.1 问题

两问：(a) narration 段的说话人身份由哪个可信源写入、写入哪个字段？
(b) 交付路径要不要从「每回合最多一段拿到音频」放宽为逐段？

### 3.2 已核实的事实

1. 【实测】**绑定层已经就位**。`voice_binding_resolver.py` 定义
   `NARRATOR_IDENTITY = "narrator"` 与 `NARRATION_PHASE = "narration"`；
   narration 段在该 resolver 中得到
   `binding_scope_for(session, presentation_identity=NARRATOR_IDENTITY, phase=NARRATION_PHASE)`。
   该 resolver 已被 `story_runtime.py` 与 `post_commit_handlers.py` 两条生产路径引用。
2. 【实测】**契约不禁忌**旁白携带说话人：`NarrativeSegment` 的 `type` 与 `speaker_id`
   之间不存在校验耦合，`speaker_id: str | None = None`，narration 段本来就能带。
3. 【实测】三处排除点确实存在（ADR-005 验收报告 §10.1 列举正确）：
   `speech_unit.py` 拒绝非 character 段；`story_runtime.py` 交付循环
   `if item.type != "character": continue`；`post_commit_handlers.py:480-486`
   候选过滤硬编码 `item.type == "character"`。
4. 【实测】封存层的错误码是 `speakerless_segment_requires_narrator_policy`，
   注释写明「在出现一个明确的旁白呈现策略之前，不允许调用方指定谁在讲」——
   **代码自己已经把这个缺口命名了**。
5. 【新核实】验收报告 §10.5 断言「phase 在交付路径上没有任何消费者，
   检索 `.phase` 只命中 `voice_identity.py`」。按其自述方法重跑：
   在 `e0edf533`（报告基线）上 `.phase` 命中 9 个以上非测试文件，
   当前 tip 上 `voice_binding_resolver.py`、`post_commit_handlers.py`、
   `story_runtime.py` 均按 phase 分支。**该断言在写下时即不成立**，现已由
   `verified_gaps` 与三条守卫更正（SB-38）。

### 3.3 验收报告 §10.5 少算的部分

§10.5 把缺口列为「最后三处接线」（契约身份、`speech_unit`、`story_runtime`）。
按当前 tip 实测，即便这三处全部补齐，旁白音频**仍然出不来**，因为还有两层：

| 漏算项 | 位置 | 后果 |
|:---|:---|:---|
| 候选过滤硬编码 `item.type == "character"` | `post_commit_handlers.py:480-486` | 旁白段即使带上身份也进不了候选（§10.1 自己列了这一点，§10.5 的清单却漏了） |
| 每回合只产一个 `AUDIO_PREPARE` + 取 `candidates[0]` + `UNIQUE(turn_id, kind, recipe_revision)` | `post_commit_work.py`、`post_commit_handlers.py:486`、迁移 `013_world_post_commit_jobs.sql` | 同一回合插不进第二个音频作业；「按身份逐段配音」在结构上不成立 |

因此 D-2(b) 不是「顺带放宽」，而是「按身份逐段配音」这句话的字面前提。
§3.2 第 1、2 条说明**身份侧已经建好**，成本集中在交付侧。

### 3.4 与 D-3 的关系

D-2(b) 与 D-3 共享同一处瓶颈：交付路径今天最多产出一段音频。
D-3 问的是「这一段要不要落 take」，D-2(b) 问的是「要不要多于一段」。
两者可分别裁定，但都落在 `post_commit_work` / 迁移 013 这一层，改动会重叠。

### 3.5 候选与代价（不选）

**(a) 旁白身份的可信源**：

| 候选 | 代价 |
|:---|:---|
| A. 由引擎写入一个场景级常量式旁白身份（类似 `SCENE_DISPLAY_NAME` 的旁白版） | 最小；但旁白成为「全局单例」，与目录里「至多一个 narration 设计」一致 |
| B. 由 `ScenarioPresentation` 增一张旁白身份表，按 locale 索引 | 与 D-1 的表同构，可合并设计；范围更大 |
| C. 不给旁白身份 | 与验收标准 1 冲突，需同时更正该标准措辞 |

**(b) 交付路径**：

| 候选 | 代价 |
|:---|:---|
| A. 维持每回合一段 | 不改代码；「按身份逐段配音」需降级表述 |
| B. 放宽为逐段 | 需要迁移（去掉或改造 `UNIQUE(turn_id, kind, recipe_revision)`）、`post_commit_work` 改为按段产出作业、handler 改为遍历候选；涉及持久化地基，按 ADR-002 需前向迁移 |
| C. 折中：一回合内「一个旁白 + 首个角色段」两段 | 同样要动迁移，但覆盖面窄；仍不满足「逐段」字面 |

### 3.6 裁定前不得做

- 不得让 narration 段进入配音路径（派发卡 `forbidden_actions` 明列）；
- 不得在 D-3 裁定前让实时路径落 take。

## 8. 依赖关系（不是建议顺序）

以下是从代码读出的因果，不是偏好：

```
D-3（实时路径是否落 take）
  └─▶ 音频 take 是否存在
        └─▶ D-2(b) 逐段交付是否有意义（多段都要各自落 take）

  └─▶ 叙述者场景披露（§2.4）
        └─▶ 与 D-2(a) 共用「谁给场景起公开名」这一可信写入点

```

换言之：**D-3 先于 D-2(b)；D-1 与 D-2(a) 共享一个可信写入点，宜一并裁定。**
